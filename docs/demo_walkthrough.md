# Demo walkthrough

This walkthrough uses the synthetic customer dataset in `sample_data/customers/customers_sensitive_review.csv` and the example policy in `config/examples/sensitive_field_policy.yaml`.

## Scenario

A team has a customer extract and wants to know which fields may need human review before sharing, migration, analysis, or downstream use.

The reviewer wants structured evidence. They do not want to paste raw rows into an LLM, and they do not want a black-box decision.

## 1. Install and run tests

```bash
python -m pip install -e ".[dev]"
python -m pytest -q
```

## 2. Run the deterministic review

```bash
python -m sensitive_field_review_agent.cli \
  --input sample_data/customers/customers_sensitive_review.csv \
  --policy config/examples/sensitive_field_policy.yaml \
  --output-dir outputs/customers_sensitive_review
```

This runs the default local workflow:

```text
intake -> policy -> profile -> signals -> review suggestions -> artifacts
```

No API key is required.

## 3. Inspect the generated artifacts

Start with the Markdown report:

```bash
cat outputs/customers_sensitive_review/sensitive_field_review_report.md
```

Then inspect the structured artifacts as needed:

- `sensitive_field_profile.json` for safe field profiles and inferred physical types
- `sensitive_field_signals.json` for deterministic pattern-family and keyword evidence
- `sensitive_field_results.json` for structured suggested policy categories and suggested review levels
- `sensitive_field_findings.csv` for a flat triage table
- `sensitive_field_trace.json` for run metadata and artifact paths

## 4. What the report is meant to show

The report highlights fields that may require review and summarizes the deterministic evidence behind each suggestion. For example, a field may have a suggested policy category because a column-name keyword matched, a pattern family produced aggregate evidence, or a policy override applied.

The report does not make final decisions. It supports field-level triage so a human reviewer can decide what handling is appropriate.

## 5. Request LLM review without an API key

```bash
python -m sensitive_field_review_agent.cli \
  --input sample_data/customers/customers_sensitive_review.csv \
  --policy config/examples/sensitive_field_policy.yaml \
  --output-dir outputs/customers_sensitive_review_llm \
  --llm-review
```

If `OPENAI_API_KEY` is not configured, the command still exits 0 after deterministic artifacts are generated. It writes:

- `llm_safe_field_summary.json`
- `llm_field_review.json`
- `llm_field_review.md`

The LLM review status records that the advisory stage was skipped or fell back. This keeps the artifact set predictable for demos and automation.

## 6. Optional real LLM setup

To run active advisory LLM review, install the optional LLM dependency and configure `OPENAI_API_KEY`:

```bash
python -m pip install -e ".[dev,llm]"
export OPENAI_API_KEY="..."
```

Then rerun the `--llm-review` command. The LLM receives only the safe deterministic evidence payload, not raw dataset rows.

## 7. What a reviewer would do next

A reviewer would use the artifacts to:

- inspect fields with suggested review levels
- compare evidence against the human-authored policy
- answer reviewer questions generated by the deterministic workflow and optional LLM review
- decide final handling outside the tool

The tool provides evidence and triage suggestions. The human reviewer makes final decisions.
